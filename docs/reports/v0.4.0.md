## 5. Findings
1. **The English MS MARCO reranker is harmful for Vietnamese**: ΔMRR@10 -0.249 [-0.265, -0.233];
   it is worse than no reranking on 1,234 questions and better on 224. The coursework system
   (`Truy_xuat_du_lieu/Final`) had this reranker switched off; this run shows that was the right call, now
   with a measurement.
2. **The multilingual reranker is much better but too slow under the chosen constraint**: ΔMRR@10
   +0.110 [+0.099, +0.121] on validation (better on 606 questions, worse on 104), recall@1 0.869 vs
   0.717; but p95 latency 1030.63 ms for 50 pairs, over the 300 ms limit.
   [Exploratory] The validation gain is large enough that a cheaper configuration (fewer pairs) is worth a
   new protocol; it was not tested on test here and makes no claim about test.

## 6. Deviations from the protocol
- recall@50 was listed in the protocol but is not in the results: the script reused the M3 scoring helper,
  whose cut-offs are 1, 5, 10, 20, 100. recall@20 and recall@100 are reported instead. No decision depended
  on recall@50.
- The estimated budget (under 60 minutes) held for the run itself (50 min), but the kernel first waited in
  Kaggle's queue for more than 170 minutes; the workflow now fails fast when queued and can fetch later (#25).
- The bot commit message names the fetch commit (`87658dc`), not the code commit that ran (`5d36348`, recorded in the JSON).

## 7. Threats to validity
1. Latency was measured with one question at a time on a T4 in float16; a different GPU, batching across
   questions or ONNX/quantisation would change it. The limit is a product assumption fixed in advance.
2. float16 was used for both rerankers; precision effects are confounded with model choice.
3. The large R2 gain is on validation only; validation was also used to tune RRF in M3.1 (mild optimism
   for the reference, which would understate, not overstate, R2's gain).
